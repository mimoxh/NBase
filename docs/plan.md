执行细节：

- P1 的图片只验证粘贴结果、引用和显示边界，真实上传和附件管理在 P3-01 完成；无法接收的图片要给出提示。

## 4. P2：建立第一条真实文档路径

目标路径：**初始化账号 → 登录 → 新建文档 → 写作 → 服务端确认保存 → 切页 / 重启 → 重开 → 导出**。本阶段使用独立测试数据库和可丢弃样例，不接触 NAS 正式 PostgreSQL 或 NocoBase。

| 任务 | 交付物 | 依赖 | 验收要点 |
| --- | --- | --- | --- |
| P2-01 数据与迁移 | 独立数据库配置、版本迁移、用户 / 工作区 / 文档模型、稳定 ID、schemaVersion、revision、错误契约 | P1 格式结论与组织决策 | 空库可建立；测试旧库可升级；迁移失败不继续接收业务写入；正文版本未知时保护原数据而非重置 |
| P2-02 最小身份与授权 | 一次性初始账号建立、登录 / 退出、会话、工作区校验；无公开注册 | P2-01 | 未登录不能读写文档；伪造工作区或文档 ID 不能越权；初始化入口不能再次接管已有实例；过期会话有明确状态 |
| P2-03 文档 API | 创建、读取、列表、改名、移动、修订更新；软删除数据与接口基础 | P2-01、P2-02 | 边界校验和事务实际执行；旧 revision 返回冲突；重试创建 / 导入不会无提示重复生成；列表有分页或明确上限 |
| P2-04 文档组织与页面接入 | 目录、创建、重命名、移动、最近打开；编辑器连接真实文档 | P1-01、P2-03；前端可先基于契约并行 | 改名 / 移动不改 ID；目录不能形成循环；快速切页不串文档；同名、空标题、无效目标有明确行为 |
| P2-05 自动保存与并发 | 编辑中、保存中、已保存、离线、失败、冲突状态；按文档隔离的串行写入 | P2-03、P2-04 | 服务端仅在写入成功后确认；仅当前最新编辑已获确认时显示已保存；旧响应不覆盖新状态；失败不阻塞继续输入 |
| P2-06 本地草稿与恢复 | 按账号 / 工作区 / 文档隔离的浏览器草稿、恢复入口、冲突另存副本 | P2-05 | 刷新 / 异常退出后可发现已写入浏览器的草稿；对比服务端版本后由用户选择；另存生成新 ID；失败重试不自动覆盖较新版本 |
| P2-07 Markdown 闭环与阶段验证 | `.md` 导入、导出、只读源码面板、转换提示、契约与浏览器验证记录 | P1-03、P2-03～P2-06 | 导入新建文档，原文件不受影响；有损转换先提示；导出范围和未保存状态明确；图片打包闭环在 P3-01 补齐 |

必须在实现前统一的契约：

1. 正式文档含稳定 ID、所属工作区、schemaVersion、revision 和内容；编辑器运行时 key 不作持久身份。具体字段与端点在 P2-01 评审，不提前建立万能对象框架。
2. 更新携带 expectedRevision，事务内条件写入，成功返回服务端接受的修订信息；冲突返回 409。拒绝无认证写入和静默 last-write-wins。
3. 断线、超时、未登录、无权限、无效格式、资源不存在和版本冲突要能分别处理。请求超时不等于服务端没有保存；响应丢失时先核对服务端状态再决定重试。
4. 草稿保留内容、基准修订、格式版本和写入时间；存储失败或容量不足要可见，并提供复制 / 导出保全路径。登出后的保留与清理规则在接入时明确，不能让下一账号直接看到前一账号内容。
5. 浏览器草稿不是备份或完整离线模式。浏览器缓存被清除、尚未落入草稿的数据和服务端故障仍有边界，不能宣称任意断电零丢失。
6. 最小认证同时明确密码安全存储、会话有效期和撤销、登录尝试限制及跨站请求防护；具体方案在 P2-02 核对官方资料后记录。单人使用不省略这些验证，外网环境配置另在 P3-07 验收。

P2 场景验收至少覆盖：

- 持续输入期间触发保存，再快速切换 A / B 文档；保存与读取结果都归属正确。
- 保存失败、断线后恢复、服务端已提交但客户端未收到响应；本地新内容不被旧快照清除。
- 同账号两个标签从同一修订开始编辑；第一次保存成功，第二次收到冲突，能保留本地内容并另存。
- 草稿与服务端同时存在更新；用户先检查内容再恢复，不能按时间戳直接强行覆盖。
- 登录失效时继续输入后重新登录；内容能找回，且不能绕过重新授权。
- 重启应用和数据库后重开文档；正文、目录关系和 ID 正确。容器重建与卷的持久性在 P3 验证。

阶段出口：真实写入和失败恢复都有证据，格式及 API 契约测试通过。此时仍属于本地功能验证，历史、完整备份和日用部署尚未验收。

备份和升级的重点约束：

- 首版优先评估短暂停写的维护窗口方案，取得数据库与附件的一致集合；若改为在线备份，必须另行证明并发写入、删除和文件落盘期间的一致性。单独 SQL dump 或单独复制附件目录不算完整备份。
- 已确认初期保留策略：每次实际成功保存留快照，历史、回收站与附件暂不自动清理，不提供永久清空入口。后续版本/空间上限按样例与预算另行决定。
- 备份失败、磁盘空间不足和附件缺失要能发现；备份副本不能只放在同一待恢复数据目录。异机 / 异盘位置、自动备份频率和可接受恢复时间在部署前确认。
- 升级前备份并校验；迁移成功后再开放写入。新 schema 不兼容旧程序时，回退走已验证的备份恢复，不能只切回旧镜像。
- 运维说明区分进程存活、数据库 / 迁移可用与产品验收状态；不能把健康检查的 200 当作备份成功或产品就绪。

## 8. 分工、风险与决策点

### 并行方式

按 AGENTS.md，每个开发阶段由集成者统一契约，多个 Agent 在独立 worktree 处理不冲突的任务。可用槽位允许时安排：

| 阶段 | Agent A | Agent B | 集成者 |
| --- | --- | --- | --- |
| P1 | 页面 / 组织交互提案 | 编辑器、Markdown 样例与风险验证 | 统一编辑器接口、集成与体验检查 |
| P2 | 存储、迁移、认证与 API | 依据冻结契约实现页面、保存与草稿 | 共享 contracts、端到端场景与合并顺序 |
| P3 | 附件 / 历史等服务端任务，按文件边界分批 | 搜索 / 恢复等界面任务，按依赖分批 | Docker、备份恢复集成与阶段验收 |

不要同时安排多个 Agent 修改同一入口文件、共享契约或 lockfile。遇到交叉改动先统一接口，再调整任务边界。未提交变更不会自动出现在新 worktree，开始前必须确认审查和实现使用的是当前重建基线；不自动提交、重置或覆盖用户改动。

### 风险与处理
