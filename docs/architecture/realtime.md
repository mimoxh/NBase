# 实时协同编辑（设计稿）

2026-11-18。优化第 5 批的设计文档。2026-11-18 用户确认四项取舍：由在线编辑者（保存者）写成修订；白板按元素后写者胜；显示他人光标与选区；离线增量存 IndexedDB。文档、行页面正文与白板均已实现（服务端与网页端，验证见 [验证记录](../validation.md)）。范围由用户确认：文档、行页面正文和白板；建立在[成员与角色](members.md)和[在场与评论](collaboration.md)之上，复用第 3 批的 WebSocket 通道。

## 目标与验收

- 多人同时编辑同一页面时实时看到对方的修改，不再靠修订冲突卡片处理。
- 正文仍经服务端校验、`expectedRevision` 写入并产生修订和历史；**服务端确认写入修订后才显示「已保存」**。
- 历史恢复、源码应用、快速记录、模板应用、导入等外部写入使房间重新载入并提示。
- 验收场景：双标签中文输入（含输入法组字）、断线重连、离线编辑后合并、服务端重启、只读成员在场（只看不写）、白板同时拖动和编辑不同元素。

## 选型

2026-11-18 已验证：`apps/web/src/editor/collab/yjsBinding.test.ts` 用两个编辑器经 Y.Doc 互相同步，Markdown 样例全部节点（含表格、公式、Mermaid、脚注、提示块、页面引用、白板嵌入）与附件、块引用、图片引用、折叠块、书签、数据库视图、块锚点往返不变，附件属性修改能同步，双方离线各改一段后交换增量能收敛。

| 依赖 | 版本 | 许可 | 用途 |
| --- | --- | --- | --- |
| yjs | 13.6.33 | MIT | CRDT 文档；网页与服务端共用（服务端只合并增量、计算状态向量，不理解正文） |
| y-protocols | 1.0.7 | MIT | 同步协议（sync step 1/2、update）与 awareness（光标、选区） |
| @lexical/yjs | 0.52.0 | MIT | 与现有 lexical 同版本；Lexical 节点树与 Y.XmlText 双向绑定、协同撤销 |
| lib0 | 0.2.120（传递依赖） | MIT | yjs 的编码工具 |

不用 y-websocket / Hocuspocus：房间、鉴权、持久化和保存规则都要接入现有成员、修订和收据体系，自写的房间层更小。版本在实现时再次核对并锁定精确版本。

正文现有 13 种自定义节点（页面引用、块引用、附件、图片引用、公式、Mermaid、脚注、折叠块、提示块、书签、白板嵌入、数据库视图等）都没有嵌套编辑器，属性都是可序列化的值，可以由 @lexical/yjs 按节点属性同步。实现第一步是逐个节点做往返测试（Lexical JSON → Y.Doc → Lexical JSON 不变）。

## 房间

- 一个页面一个房间，房间状态是一个 Y.Doc：
  - 文档与行页面：`root`（@lexical/yjs 的 XmlText）加 `meta` Map 里的 `title`（Y.Text）。
  - 白板：`elements`（Y.Map，键是元素 ID，值是整个元素的 JSON）、`order`（Y.Array，元素 ID 的 z 序）、`title`。并发修改同一元素时以元素为单位后写者胜；不同元素互不影响。
- 复用 `/api/workspaces/:id/live` 连接，按页面订阅房间（一条连接可同时订阅当前页和至多 12 个嵌入页面）。消息为二进制帧：`[类型][页面 ID][epoch][y-protocols 消息]`。
- 只读成员可以加入房间、接收更新和 awareness，服务端丢弃其发出的文档更新。
- 房间按需载入：第一个订阅者到来时从数据库读出快照与增量；最后一个订阅者离开 60 秒后从内存卸载。

### 持久化（新迁移）

- `page_collab_rooms`：`page_id`、`epoch`（房间代数）、`base_revision`（房间从哪个修订建立）、`saved_revision`、`saved_state_vector`、`snapshot`（合并后的 Y 状态）、`updated_at`。
- `page_collab_updates`：`page_id`、`epoch`、`seq`、`update`（bytea）、`user_id`、`created_at`。每条更新**先写库再广播并回执**，所以服务端确认过的增量不会因服务重启丢失。
- 压缩：增量超过 200 条或 1 MiB，或每次保存成功后，服务端用 `Y.mergeUpdates` 合并进 `snapshot` 并删除旧增量。Y 状态超过 8 MiB 时以最新修订重建房间（epoch + 1）。
- 备份：两张表照常登记进备份引擎（引擎要求库里每张表都有登记），但修订才是权威数据，恢复备份时在撤销分享链接的同一事务里清空两张表，客户端重连后从修订重新建立房间。

### 初始化

房间不存在或 epoch 变化后，服务端只允许**一个**客户端用当前修订的正文播种（`seed` 授权），其余客户端等待播种结果，避免两份初始内容重复插入。播种者断开时授权转给下一个编辑者。

## 保存（修订）

服务端不运行 Lexical，所以由一个客户端把 Y.Doc 还原为 Lexical JSON 写成修订：

- **保存者**：服务端在房间里指定一个在线编辑者（最早加入者），断开时转给下一位。只有保存者调用 `PUT /pages/:id`。
- 时机：最后一次修改后 1.5 秒，持续输入时最长 10 秒一次；离开页面、切换页面前立即保存一次。
- 请求沿用现有接口与收据，另带 `collab: { epoch, stateVector }`。服务端在同一事务里锁住房间行：`epoch` 必须与房间一致；新状态向量不能落后于已记录的 `saved_state_vector`（保存者交接时旧保存者迟到的请求以 409 `COLLAB_STALE` 拒绝，客户端忽略）。满足这两条时，协同保存写在当前修订之上，不要求 `expectedRevision` 等于当前修订，因为期间只可能有不改正文的写入（改名、图标、封面、移动）。成功后记录 `saved_revision` 与 `saved_state_vector`，广播 `saved`。
- 保存者只在 Y.Doc 的正文或标题变化时才写对应字段；页面其余属性仍走原来的写接口。
- **「已保存」**：每个客户端比较自己的本地修改是否都包含在 `saved_state_vector` 中（按自己的 Yjs clientID 时钟），包含才显示已保存；只被服务端收下、尚未写成修订时显示「已同步，等待保存」；还未被服务端回执时显示「保存中」/「离线，修改保存在本机」。
- 校验失败（422）：保存者显示错误，房间继续协同；所有人看到「未能保存」，直到有人改正内容。
- 保存者离线且房间还有未写成修订的增量：下一个进入房间的编辑者成为保存者并补写。页面信息里显示「有尚未写入修订的协同修改」。没有任何编辑者再打开时，这部分修改只存在于房间表中，搜索、导出和历史看到的是上一个修订（已知限制，见下）。

## 外部写入

- **只改标题**的普通写入（目录里改名等）：服务端把新标题作为一次服务端产生的 Y 更新写进房间的 `title`（同样先落库再广播），房间不重置。图标、封面、移动、排序不在 Y.Doc 里，与房间无关。
- **改正文**的其他写入（历史恢复、Markdown 源码应用、快速记录与每日笔记追加、模板应用、导入、关闭协同的客户端的普通保存、行页面由其他路径写入）在同一事务里使房间 `epoch + 1`、`base_revision` 设为新修订并清空快照与增量；提交后服务端向订阅者广播 `reset`，再按「初始化」重新播种：
  - 没有未回执本地修改的客户端直接载入新内容，并提示「某人恢复了历史版本 / 应用了源码，页面已重新载入」。
  - 有未回执本地修改的客户端（例如离线期间写的）不合并进新房间，把本地内容保存为冲突草稿，沿用现有冲突卡片（另存为副本、下载、放弃）。

## 离线与重连

- 本地 Y 增量写入 IndexedDB（按用户、工作区、页面、epoch 隔离），关闭标签页后再打开仍在。替代协同页面上现有的 localStorage 草稿；非协同页面（关闭功能时）仍用原草稿。
- 重连后交换状态向量，只补发对方缺少的部分；epoch 已变化时按「外部写入」处理。
- 浏览器触发 `offline` 事件时立即关闭实时连接进入离线状态，`online` 事件时立即重连；其余断线由 70 秒静默检测发现。
- 服务端重启：客户端按第 3 批的退避重连，房间从库里的快照与增量恢复，服务端回执过的修改不丢。

## 撤销、光标与在场

- 撤销 / 重做改用 Yjs UndoManager，只撤销自己的修改；白板沿用自己的历史栈，撤销时生成反向的元素修改。
- awareness 广播光标与选区：文档中显示他人的光标与名字标签；白板显示他人选中的元素描边。awareness 不落库。
- 第 3 批的在场头像与「正在编辑」继续使用；协同页面上不再显示「保存了新版本，载入新版本」提示。

## 白板细节

- 写入粒度：手势结束的 `commit` 产生一次 Y 事务（一组元素的整体替换、插入、删除、z 序调整）；手势中的 `preview` 只发 awareness（对方看到拖动中的位置），不写文档。
- 文字编辑：输入期间按元素整体写入，同一元素被两人同时编辑时后写者胜（并提示对方正在编辑这个元素）。
- 规范化：保存者在还原内容前运行现有的保存前规范化（解除指向已删除元素的连接线绑定、断开因并发换父节点形成的导图环），并把修正写回 Y.Doc，所有人因此收敛到同一结果。

## 消息（已实现）

契约在 `packages/contracts/src/realtime.ts`（`RoomFrame`、`RoomServerMessage`、`CollabWrite`）。

- 文本帧（JSON，沿用第 3 批的 1 KB 上限）：客户端 `{ t: 'join', pageId }`、`{ t: 'leave', pageId }`；服务端：
  - `room`（epoch、baseRevision、savedRevision、savedStateVector、seed、saver、readOnly）：加入后的房间状态与本人角色；重置后客户端重新 join，服务端再发一次带新 epoch 的 `room`。
  - `roomRole`（epoch、seed、saver）：播种者 / 保存者角色变化。
  - `roomSaved`（epoch、revision、stateVector、by）：保存者写入修订成功。
  - `roomReset`（epoch、revision、reason：restore / source / write / rebuild、by）：外部写入重置房间，epoch 是新代数。
  - `roomError`（code：NOT_FOUND / PAGE_KIND_INVALID / ROOM_LIMIT / SERVICE_UNAVAILABLE / REALTIME_DISABLED）。
- 二进制帧：21 字节头 `[类型 1][页面 ID 16][epoch 4，大端]` 加内容；单帧不超过 256 KB，每连接每秒最多 50 条。类型 0 `state`：内容是发送方的 Yjs 状态向量，接收方回以发送方缺少的增量（取代 y-protocols 的 step 1 / step 2 握手）；类型 1 `update`：一条 Yjs 增量；类型 2 `awareness`：y-protocols awareness 更新；类型 3 `ack`（仅服务端到客户端）：内容是服务端存下这条增量后房间的状态向量，客户端据此判断自己的修改是否已被服务端收下。epoch 不一致的帧直接丢弃。
- 服务端收到 `update` 时先解码校验、写库，再应用到内存中的 Y.Doc 并转发；收到 `state` 时回以对方缺少的 `update`，再发自己的 `state` 以取回客户端离线期间的修改。

## 网页端实现（2026-11-18）

- 房间客户端在 `apps/web/src/persistence/collab/roomClient.ts`，本地增量存 IndexedDB（`roomStore.ts`，按用户、工作区、页面、epoch 隔离；无 IndexedDB 时退化为内存存储，仅供测试）。协同页面不再写 localStorage 草稿；回退到单人模式时才把未保存内容转成普通草稿。
- 播种：收到 `room` 且 `seed` 为真时用打开页面的正文建立 Y.Doc 并广播。其余客户端在编辑器挂载前先连房间（provider 可以先挂起，等房间内容就绪再绑定），避免空房间各播一份。
- 保存者：最后一次修改约 1.5 秒后、持续输入最长 10 秒保存一次，沿用现有写入接口与收据，另带 `collab: { epoch, stateVector }`；409 `COLLAB_STALE` / `COLLAB_EPOCH` 静默忽略（交接后的迟到请求），400 / 422 显示「未能保存」，其余错误重试；离开页面、切页、`pagehide` 时立即保存一次。回收站、恢复、改图标等写操作前用 `whenSaved(10s)` 等协同保存落定，超时提示「协同修改尚未保存完成，请稍后再试。」
- 状态：有未回执的本地增量显示「保存中」；全部回执但尚未写成修订显示「已同步，等待保存」；`roomSaved.stateVector` 覆盖自己的 clientID 时钟后显示「已保存」；离线且本地有记录显示「离线，修改保存在本机」。
- 输入法组字期间（composition）不应用远端增量，先排入队列，组字结束后重放，避免打断候选。
- 等待回退：非播种者加入后 12 秒仍无房间内容（没有播种者或保存者到来）时回退到单人模式并提示，而不是无限等待。
- `roomReset`：没有未回执修改的客户端重新载入并提示「某人恢复了历史版本，页面已重新载入」或「页面内容已在服务端更新，已重新载入」；有未回执修改的客户端进入冲突视图（只保留该条本地记录的离线房间客户端），横幅提供「另存为副本 / 下载 / 放弃修改，载入服务端版本」。
- 编辑器：`CollaborationPlugin` 的 `initialEditorState` 用打开时的正文播种；房间未就绪时不挂载编辑器（显示「正在连接协同…」占位），就绪后才挂载，因此不需要中途切换只读状态。他人光标与名字标签样式在 `editor.css`（`.nbase-collab-cursor` / `.nbase-collab-name`，颜色经 `--lexical-cursor-color` 变量）。
- 嵌入页面不入房间（沿用单人保存路径），`roomSubscriptionLimit` 13 留给后续嵌入房间；回收站与恢复操作跳过房间持有页面的本地草稿步骤。`NBASE_REALTIME=off` 或 `roomError`（REALTIME_DISABLED）时本会话不再入房。

## 白板网页端实现（2026-11-18）

- Y 适配层在 `apps/web/src/whiteboard/collab.ts`（`WhiteboardBinding`）：`elements` 是 Y.Map（元素 ID → 整个元素 JSON），`order` 是元素 ID 的 Y.Array。读取时以 `order` 为准，`order` 缺失的元素按 ID 补在末尾，重复或已删除的 ID 在下一次本地写入时清理；本地写入只把本次手势新增、删除、移动的 ID 写进 `order`，不覆盖他人同时插入的 ID。
- `store.commit` 一次产生一个 Y 事务；`preview`（拖动、缩放、绘制中）只写 awareness 的 `previews`，他人以半透明描边看到位置，手势结束或取消后清除。awareness 还带 `selection`（他人选中描边与名字）和 `editingId`（同一元素有人正在编辑时提示「某人也在编辑此元素；同一元素后写者胜。」）。
- 撤销 / 重做：白板沿用自己的历史栈，只记录本人事务（Y 事务 origin 区分），撤销时生成反向的元素修改；某元素在本人修改之后又被他人改过时，撤销跳过该元素，不覆盖他人的修改。
- 保存者在写成修订前运行 `normalizedWhiteboardContent`：沿用 `normalizeForSave`（解除指向已删除元素的连接线绑定，新增断开并发换父节点形成的导图环），修正以单独 origin 写回 Y.Doc，不进入任何人的撤销栈。
- 播种：`seed` 为真的客户端用打开时的白板内容建立 Y.Doc；其余客户端在房间内容就绪前显示「正在连接协同…」。只读成员不显示编辑工具，手势不写入。房间重置、离线、回退单人与文档页面共用同一个房间客户端和状态文案。
- 嵌入在文档里的白板不入房间（与嵌入页面相同）。
## 安全与限制

- 订阅时检查会话、成员关系与页面所在工作区；角色变化或被移除时按第 3 批规则以 4401 关闭。
- 单条更新不超过 256 KB，每个连接每秒最多 50 条文档更新；超过即断开。
- 服务端不解析正文结构，无法拒绝编辑者构造的异常 Y 更新；影响局限于该房间，所有者可以用「从最新修订重建协同状态」恢复（epoch + 1）。最终写入的修订仍经完整校验。
- `NBASE_REALTIME=off` 关闭协同，回到现有的单人保存与冲突卡片。

## 改动范围（已按此实现）

- 服务端：`live/` 增加房间管理与二进制消息；新迁移两张表；`pages/repository.ts` 的写入检查 `collab` 字段并在外部写入时重置房间；恢复备份时清表；路由审计与 `collaboration-db` 之外新增 `realtime-db` 测试（多客户端同步、保存者转移、外部写入重置、重启恢复、viewer 写入被丢弃）。
- 网页：`editor/` 接入 @lexical/yjs（替换 HistoryPlugin 为协同撤销）；`persistence/` 新增房间客户端与 IndexedDB 存储，`usePageSaver` 在协同页面上改由房间驱动；白板 Y 适配层在 `whiteboard/collab.ts`，`store.ts` 接收远端状态；嵌入页面暂不入房间。
- 契约：`packages/contracts` 新增房间消息类型与 `collab` 写入字段。

## 已知限制（计划）

- 只有单个服务进程；多实例部署需要共享房间状态，另行设计。
- 没有编辑者在线时，已同步但未写成修订的修改不进入搜索、导出和历史，直到下次有编辑者打开页面。
- 白板同一元素的并发编辑以元素为单位后写者胜，不做字符级合并。
- 多维表格单元格、数据库结构不在本批范围内（仍走现有写入与冲突规则）；行页面只协同正文。
