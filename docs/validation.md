结论：搜索、单页读写和历史在此规模下都在数十毫秒内，暂不需要专用搜索索引或服务。主要瓶颈是目录 N+1 请求（随页面数线性增长，网络延迟更高时更慢），其次是长文档每次按键都要多次完整生成快照（含 Markdown 导出）并重渲 O(n²) 的目录。收据表保存完整响应，正文实际按“版本 + 收据”存了两份；在不自动清理的策略下，大文档频繁保存会较快增长，留作后续保留策略的输入，本阶段不改动收据契约。

### 优化

- 新增 `GET /api/workspaces/:workspaceId/page-tree`：用递归 CTE 一次返回从未删除根页、经未删除父页可达的页面，按 created_at、id 排序，上限 2000，超出返回 `truncated` 由网页报 PAGE_LIMIT_EXCEEDED；成员关系与原列表接口同样校验。原分页列表接口保留。
- 编辑器的标题锚点改用 `$collectOutline()`，不再完整生成快照；工作台不再在每次渲染时导出 Markdown，改为只在打开源码面板或导出时计算；目录 `Tree` 改为 memo + 父子映射，回调保持稳定。草稿写入、签名比较与保存调度不变。
- Vite 拆分 react、lexical 和应用代码：117.08 / 218.78 / 378.28 kB（gzip 36.59 / 68.26 / 117.95 kB），不再有 500 kB 提示。总下载量基本不变，好处是应用更新时可复用缓存的第三方库。

## 2026-11-08：多维表格扩展（`feat/database-expansion`）

范围见 [需求记录](product/requirements.md) 的 2026-11-08 补充。各阶段结果按顺序记录。

### 阶段 0：拆分与基线

`DatabaseView.tsx` 按职责拆成工具条、表头菜单和表格组件，行为不变。`source.ts` 的拆分和第 3 阶段的数据层合并进行，避免做两遍。

基准脚本 `npm run bench:db --workspace @nbase/server`，在 `127.0.0.1:54329` 的一次性库中运行，结束后删库。2.5 万行合成数据，行正文为空。PostgreSQL 绑定 2 个逻辑核，不等于 N150。`blockedWriteMs` 是同时发起的一次页面创建要等待的时间。

### 阶段 1：降低持锁操作

- 选项改色、排序等不影响搜索的结构修改，不再重算行。影响搜索时，500 行以内在事务内重算，更大的库交给后台 worker，分批、不持工作区锁、重启后续跑（迁移 v14）。
- `setPosition` 只读相邻行，间隙用尽时重排周围一段，逐步扩大。
- 随数据库一起进回收站的行不改版本号、不写快照，也不再单独出现在回收站列表。

| 操作 | 修复前 ms | 修复后 ms | 阻塞其他写入 ms |
| --- | --- | --- | --- |
| 改一个选项颜色 | 1164 | 23 | 7 |
| 移动一行 | 22 | 22 | 11 |
| 整库进回收站 | 1874 | 952 | 946 |
| 整库恢复 | 2068 | 1080 | 1062 |

**未达预算：** 整库进回收站和恢复仍约 1 秒，超过 250 ms 的目标，时间花在改写 2.5 万行及其索引上。这两个操作很少发生，期间其他写入是排队等待而不是失败，本机草稿也不受影响，所以接受这个例外。把它拆成后台分批会让回收站中的库的行短暂可见，风险更大。`test:db` 14 项通过。

### 阶段 2：服务端查询

新增 `POST /databases/:id/query` 和 `/rows/read`（迁移 v15 增加 ICU 排序规则 `nbase_zh`）。筛选支持 OR 组和相对日期，`evaluateView` 接收时区上下文。两边运行同一份 `resolveFilters` 结果。

`database-query-db.test.ts` 把每种字段、每个操作符、每个取样值和每个排序方向，逐一对比 SQL 和 `evaluateView` 的结果（150 多种组合，含改过类型的值、已删选项、非法日期、半填条件、时区跨日）。修复过程中，测试抓住了一个按文本别名排序的错误。`test:db` 15 项通过，服务端单元 52 项通过。

### 阶段 3：前端数据层

表格只保存完整的行 ID 顺序，行内容按滚动位置分窗读取，最多缓存 3000 行，有待写入的行不会被淘汰。自己的编辑在原地更新；如果编辑影响了当前的筛选或排序，页脚显示“结果可能已变化，刷新”，行不会突然消失。

`rowStore.test.ts` 6 项覆盖分窗读取、写入中的行不被淘汰、版本号串联、旧数据不覆盖新数据、本地增删移动和保存失败。演示工作台走查了筛选、编辑后刷新、新建、删除、拖动排序（模拟事件）和打开行页面，没有发现渲染循环。大表滚动在第 4 阶段上限提高后验证。

### 阶段 4：批量接口与 3 万行上限

新增 `POST /databases/:id/rows/bulk`（create、patch、trash、duplicate），每块最多 500 行，用集合式 SQL，每行写一个版本，块上有操作收据可重试。数字、日期和复选框的修改不读正文。批量删除每行自成删除组，可单独恢复。单库上限提高到 30,000 行。

2.5 万行分 500 一块导入共 2.2 秒，单块 p50 32 ms、p95 44 ms，同时进行的文档保存 p50 4 ms、p95 5 ms、最慢 32 ms。

持久化工作台（一次性库 `nbase_p2_ui_fixture`，构建产物，端口 4331）打开 2.5 万行：共渲染 37～62 行；跳到 1/4、中部、末尾和 60 万像素处定位都正确，没有残留的加载占位行；在远端行上编辑并保存成功。窗格隐藏时浏览器不触发滚动事件和动画帧，这次用手动派发事件和定时器代替，**真实拖动滚动条的流畅度未验证**。

### 阶段 5：选项、键盘与批量界面

字段菜单可以改名、改色、拖动或上下移动、新建和删除选项（重名被拒绝，删除后已选的行显示为空，指向该选项的筛选条件一并移除）。表格有单元格光标：方向键、Tab、Enter、Esc、Home/End、Delete；Shift 扩展选区；直接输入替换内容；回车和 Tab 提交后继续移动。复制粘贴用 `copy`/`paste` 事件和 TSV，不用 `navigator.clipboard`。修复了已删选项的 ID 被重新提交导致 422 的问题。多行选择支持批量改字段、复制和移入回收站，单行也可复制。

演示工作台走查了以上操作和 2×2 粘贴（类型不符的单元格被跳过并提示）、复制（TSV 内容正确）、删除清空。键盘、粘贴和中文输入用脚本派发事件模拟，**实体中文输入法和系统剪贴板未测**；选区里未载入的行不会被复制，会提示数量。

### 阶段 6：CSV 与数据库导出

工具条增加“导入导出”：CSV 导入（UTF-8、GBK，字段映射，可新建字段和选项，类型不符的单元格留空并提示）、CSV 导出（当前视图或全部字段，UTF-8 BOM，文本开头的 `=+-@` 加撇号防公式）。导入按固定分块和固定操作 ID 发送，失败后在对话框里继续不会重复建行；刷新页面后不能续传。ZIP 导出含 `rows.csv`、`database.json` 和各行正文，复用子树打包，最多 199 行。

单元测试覆盖中文、引号、换行往返，公式防护，分隔符识别，GBK，3 万行解析，续传。演示工作台走查了导出内容和导入流程。ZIP 导出在第 12 阶段的持久化走查中验证。

**已知差异：** URL 校验在 SQL 里是模式近似；文本大小写折叠和排序依赖 Node 与 PostgreSQL 各自的 ICU 版本，只影响少数字符的顺序。N150 上的实际耗时未测。
